# Сервер «Еда и здоровье»

**Установка с нуля и переезд на другой сервер — пошагово в [INSTALL.md](INSTALL.md).**

FastAPI + SQLite (ТЗ, раздел 9). Точка обмена и резервная копия данных семьи; телефоны от него не зависят.

## Данные и настройки

Всё состояние сервера — одна папка `FH_DATA_DIR`:

```
fh.db       база (SQLite, WAL)
photos/     фото кастрюль, <id>.jpg
```

Переезд на другой сервер: установка + перенос этой папки. Настройки — только переменные окружения:

| Переменная      | Что это                                            |
|-----------------|----------------------------------------------------|
| `FH_FAMILY_KEY` | ключ семьи, не короче 16 символов; в репозиторий не попадает |
| `FH_DATA_DIR`   | папка данных (по умолчанию `./data`)               |
| `FH_TELEGRAM_TOKEN` | токен бота от @BotFather; без него рассылки нет |
| `FH_TELEGRAM_CONFIG` | кто чьи отчёты получает (по умолчанию `/etc/foodhealth/telegram.json`) |
| `FH_REPORTS_CONFIG` | настройки отчётов (по умолчанию `/etc/foodhealth/reports.json`) |

## Запуск для разработки

```
python3 -m venv .venv
.venv/bin/pip install -r requirements-dev.txt
.venv/bin/python -m pytest
.venv/bin/shellcheck -x deploy/*.sh
FH_FAMILY_KEY=... FH_DATA_DIR=... .venv/bin/uvicorn --factory app.main:create_app --host 127.0.0.1 --port 8765
```

## Установка и обновление

Из клона репозитория, один раз ввести пароль sudo:

```
git pull
sudo bash server/deploy/install.sh 51434.koara.live
```

Скрипт ставит Python-окружение и Caddy, заводит пользователя `foodhealth`, systemd-сервис, HTTPS
(сертификат Let's Encrypt выпускает и продлевает Caddy), открывает 80/443 в ufw и включает ежедневные
резервные копии. При первой установке создаёт и показывает ключ семьи. Повторный запуск — это обновление:
код и зависимости обновляются, ключ и данные не меняются.

| Что            | Где                               |
|----------------|-----------------------------------|
| код и venv     | `/opt/foodhealth`                 |
| данные         | `/var/lib/foodhealth`             |
| ключ семьи     | `/etc/foodhealth/env` (`sudo cat`)|
| копии          | `/var/backups/foodhealth`         |
| журнал         | `journalctl -u foodhealth`        |

## Резервные копии

Каждый день в 03:30 (таймер `foodhealth-backup.timer`), хранятся 30 последних. База — согласованная копия
SQLite (сжата), фото — жёсткие ссылки на предыдущую копию, если не менялись.

```
sudo bash server/deploy/backup-now.sh                                   # копия прямо сейчас
sudo bash server/deploy/restore.sh /var/backups/foodhealth/2026-09-29_033000   # откат на копию
```

Перед восстановлением текущие данные сохраняются отдельной копией.

## Ненужные фото кастрюль

Раз в сутки, перед резервной копией, удаляются фото, на которые не ссылается ни одна кастрюля
(в том числе удалённая — её показывают сохранённые варки), и оборванные загрузки. Файлы моложе суток
не трогаются. Вручную (чистка и сразу копия): `sudo bash server/deploy/backup-now.sh`.

## Отчёты в Telegram

Каждый день в 6:00 по Москве таймер `foodhealth-reports` присылает итоги вчерашнего дня (ТЗ 17.7),
по понедельникам — ещё и итоги прошлой недели с графиками (17.6). Бот только отправляет сообщения,
команд не слушает.

1. В Telegram: @BotFather → `/newbot` → получить токен.
2. Каждый пишет боту `/start` (Telegram хранит сообщения боту около суток — настройте в течение дня).
3. `sudo bash server/deploy/telegram-setup.sh` — спросит токен, покажет написавших и для каждого
   спросит, чьи отчёты присылать; каждому уйдёт пробное сообщение. Повторный запуск — изменить привязку
   или добавить человека; `--new-token` — сменить токен.

Отправить сейчас (например, проверить): `sudo bash server/deploy/send-reports.sh [--date ГГГГ-ММ-ДД]`;
`--week` — только недельный, `--force` — заново уже отправленное.
Уже отправленное повторно не уходит (`telegram-sent.json` в папке данных). Если Telegram недоступен —
ещё две попытки через 5 и 20 минут; журнал: `journalctl -u foodhealth-reports`.

Токен лежит в `/etc/foodhealth/env`, получатели — в `/etc/foodhealth/telegram.json`
(`{"recipients": [{"chat_id", "name", "profiles": [id профилей]}]}`), его можно править руками.

### Настройки отчётов

`/etc/foodhealth/reports.json` — время приёмов пищи для раздела «Углеводы по времени приёма» (профиль с СД1).
Приём относится к первому интервалу, у которого время раньше `until`; у последнего `until` нет:
```json
{"meal_slots": [{"name": "Завтрак", "until": "11:00"}, {"name": "Обед", "until": "16:00"},
                {"name": "Ужин", "until": "21:00"}, {"name": "Поздний приём"}]}
```
Файл читается при каждом отчёте — правка действует сразу, перезапуск не нужен. Если в нём ошибка,
берутся значения по умолчанию, а причина пишется в журнал сервиса.

## Переезд на другой сервер

На старом:
```
sudo bash server/deploy/export.sh          # foodhealth-export-ДАТА.tar.gz: данные, ключ семьи, Telegram
```
На новом (после клонирования репозитория и переноса архива):
```
sudo bash server/deploy/install.sh НОВЫЙ-ДОМЕН
sudo bash server/deploy/restore.sh foodhealth-export-ДАТА.tar.gz
```
Ключ семьи переезжает вместе с данными, поэтому телефоны перенастраивать не нужно, кроме случая,
когда меняется адрес. Настройки Telegram (токен и получатели) тоже переезжают.
Архив содержит ключ и токен — храните его аккуратно.

## Протокол

Каждый запрос — с заголовком `X-Family-Key`, без него или с неверным ключом — `401`.

### `GET /health`
`{"status": "ok", "records": 123}` — для кнопки «Проверить соединение» (проверяет и ключ).

### `POST /sync`
```json
{
  "device_id": "…",
  "cursor": 0,
  "changes": [
    {"table": "product", "id": "uuid", "data": {…}, "updated_at": 1700000000000, "deleted": false}
  ]
}
```
Ответ:
```json
{"cursor": 42, "has_more": false, "changes": [{"table": "…", "id": "…", "data": {…}, "updated_at": …, "deleted": …, "device_id": "…"}]}
```

- Сервер хранит записи как есть (`data` — JSON сущности), схему не знает: новые поля и миграции Room сервер не затрагивают.
  Таблицы — только из списка `TABLES` в `app/db.py`, иначе `400`.
- Каждое изменение получает `seq` — монотонный номер на сервере. Курсор телефона — последний полученный `seq`
  (не время: часы телефонов расходятся).
- Конфликт: побеждает изменение, пришедшее на сервер позже (ТЗ 6).
- Удаление мягкое: `deleted: true` передаётся как обычное изменение.
- В ответ — изменения после курсора порциями до 1000, `has_more` — есть ли ещё (повторить запрос с новым курсором).
  Не возвращаются изменения из этого же запроса, а при `cursor > 0` — все записи, последним изменённые этим телефоном.
  `cursor = 0` — полная загрузка (новый телефон, очистка базы), свои прежние записи тоже приходят.
- До 5000 изменений за запрос.

### `PUT /photos/{id}`
Тело — JPEG (до 5 МБ). `id` задаёт телефон: это UUID из имени файла фото, одинаковый на всех телефонах,
поэтому поле `photo` в записи кастрюли и есть ссылка на фото. Повторная загрузка безопасна — фото
неизменяемы, существующее не перезаписывается. Ответ `{"id": "…"}`. Кривой id — `422`, не JPEG — `415`,
больше 5 МБ — `413`.

### `GET /photos/{id}`
Файл `image/jpeg` или `404` (например, другой телефон ещё не успел загрузить фото).

### `GET /reports/day?profile_id=…&date=ГГГГ-ММ-ДД`
Итоги дня одного человека (ТЗ 17.5) по тому, что дошло до сервера; сутки — по Москве. Отчёт не хранится,
строится заново при каждом запросе. Ответ — JSON: `title`, `incomplete`, `empty`, `summary` (выжимка) и
`sections` (подробности); строка — `{"spans": [{"text", "bold"}], "style"}`, `style`: `normal`, `big`, `warn`,
`muted`. Неизвестный или удалённый профиль — `404`, неверная дата — `422`.

### `GET /reports/week?profile_id=…&date=ГГГГ-ММ-ДД`
Итоги недели (понедельник — воскресенье), в которую входит `date` (ТЗ 17.6). Ответ — как у дневного,
плюс `last` (последний день) и `images`: `[{"id", "title", "png"}]`, PNG в base64. Графики рисуются
только при данных.
