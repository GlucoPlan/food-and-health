# ТЗ: «Еда и здоровье», версия 1

Черновик от 25.09.2026. Документ живёт в репозитории проекта, все изменения требований вносятся сюда.

---

## 1. Цель

Android-приложение «Еда и здоровье» для семьи из трёх человек: удобно взвешивать и записывать еду, считать КБЖУ, вести общую базу продуктов, блюд и кастрюль и синхронизировать всё через свой сервер. Собранные данные потом используются для отчётов и анализа (это следующие этапы, не версия 1).

Новый проект, пишется с нуля. Из старого GlucoPlan переносятся только отдельные куски кода: логика блюд и кастрюль, механизм обновления, CI. Старые данные не переносятся.

### Принципы

1. **Ввод должен быть быстрым.** Главный критерий качества — сколько нажатий и секунд уходит на запись приёма пищи.
2. **Телефон работает без интернета.** Все функции доступны офлайн, синхронизация догоняет, когда появляется сеть.
3. **История не меняется задним числом.** Правка продукта или блюда не должна тихо менять состав прошлых приёмов пищи (см. 5.4).
4. **Лучше меньше, но удобно.** Функции добавляются этапами, только когда в них появилась реальная потребность.

## 2. Пользователи и профили

- Три профиля: Иван, жена, дочь. Профили — общая сущность, синхронизируются между телефонами. Новый профиль можно добавить с любого телефона.
- Паролей и прав доступа нет, все могут всё.
- У каждого телефона есть **владелец**: профиль, выбранный в настройках при первом запуске из списка профилей. Выбор хранится только на этом телефоне.
- При записи приёма пищи вверху экрана выбирается, **кому** он записывается. По умолчанию это владелец телефона, переключается одним нажатием.
- У профиля есть флаг **«Дневник СД1»** (см. раздел 7). Включён только у дочери.
- Поля профиля: имя, флаг «Дневник СД1», показывать ли ХЕ (по умолчанию выключено), граммов углеводов в 1 ХЕ (только при включённом показе ХЕ).

## 3. Архитектура

```
 Телефон 1 ─┐
 Телефон 2 ─┼──HTTPS──  Сервер (Германия, Linux)
 Телефон 3 ─┘            API на Python + SQLite
```

- **Телефон:** Kotlin, Jetpack Compose, Room, Hilt (тот же стек, что в GlucoPlan). Локальная база — полноценная копия данных семьи.
- **Сервер:** Python (FastAPI), база SQLite, HTTPS, работает как systemd-сервис. Сервер — точка обмена и резервная копия, но телефон от него не зависит.
- **Общие данные** (видны и редактируются всеми): профили, продукты, кастрюли, блюда.
- **Личные данные:** приёмы пищи. Каждый хранится с идентификатором профиля. Видеть историю других профилей на телефоне можно (например, мама смотрит, что дочь ела с папой).

## 4. Экраны версии 1

Нижняя навигация: **Приём пищи · История · Продукты · Блюда · Настройки**. Кастрюли открываются из экрана «Блюда» или из настроек.

### 4.1. Приём пищи (главный экран)

- Вверху: выбор профиля («кому») и время приёма. По умолчанию время текущее, его можно изменить на прошедшее.
- Список позиций приёма. У каждой видны название, вес и КБЖУ порции; вес редактируется прямо в строке.
- Добавление позиции:
  - один общий поиск по продуктам и блюдам;
  - в начале списка без ввода текста стоят недавние и частые позиции этого профиля;
  - после выбора сразу открывается цифровая клавиатура для веса;
  - для продукта со средним весом штуки можно ввести количество штук вместо граммов;
  - кнопка сканера штрихкода рядом с поиском: найденный продукт сразу добавляется, ненайденный открывает создание продукта с уже заполненным штрихкодом.
- Внизу итоги приёма: ккал, Б, Ж, У.
- Кнопка «Записать» сохраняет приём и очищает экран. Незаписанный приём не теряется при переключении вкладок и перезапуске приложения.
- Если у выбранного профиля включён «Дневник СД1», дополнительно показываются поля из раздела 7.

### 4.2. История

- Список приёмов по дням, фильтр по профилю (по умолчанию владелец телефона) и по дате.
- У дня видны итоги КБЖУ, у приёма — время, состав и итоги.
- Приём можно открыть, отредактировать (вес позиций, время, состав) и удалить.
- «Повторить»: загрузить состав приёма на экран «Приём пищи» как новый приём.

### 4.3. Продукты

- Список с поиском (по названию и штрихкоду, в том числе сканером) и сортировкой (по названию, калориям, белкам, углеводам, ГИ). В строке — название и КБЖУ на 100 г.
- Карточка продукта:
  - **основное:** название, производитель (необязательно), штрихкод (необязательно, уникален, если указан; вводится вручную или сканером);
  - **на 100 г:** ккал, белки, жиры, углеводы, ГИ; необязательно: клетчатка, сахара, соль;
  - **средний вес штуки** в граммах, необязательно;
  - **источник данных:** этикетка / справочник / оценка / вручную;
  - **витамины и минералы:** раскрывающийся блок, все поля необязательные (см. 5.2);
  - заметка.
- Продукт можно удалить. Удаление мягкое: продукт пропадает из списков и поиска, но прошлые приёмы и блюда, где он использован, продолжают считаться.

### 4.4. Блюда

- Список блюд с поиском, в строке — КБЖУ на 100 г и дата последней варки.
- Редактор блюда:
  - название;
  - состав: продукты из базы с весом каждого, продукт в состав добавляется так же быстро, как в приём пищи;
  - выбор кастрюли из списка (с миниатюрой фото) и вес готового блюда вместе с кастрюлей;
  - приложение вычитает вес кастрюли и показывает вес нетто и КБЖУ на 100 г;
  - если вес не указан, расчёт идёт по сумме сырых ингредиентов, с явной пометкой об этом.
- «Сварил заново»: создаёт новую версию блюда на основе текущей. Состав и вес правятся под новую варку, старые приёмы пищи остаются со старой версией (см. 5.4).

### 4.5. Кастрюли

- Название, вес, фото (камера или галерея). Фото синхронизируется между телефонами.

### 4.6. Настройки

- Владелец этого телефона (выбор из профилей).
- Профили: список, добавление, редактирование, флаг «Дневник СД1», показ ХЕ и граммов в ХЕ.
- Сервер: адрес и ключ семьи, кнопка «Проверить соединение».
- Синхронизация: время последней успешной, кнопка «Синхронизировать сейчас», признак ошибки.
- Обновление: текущая и доступная версия, кнопки «Обновить» и «Проверить сейчас» (см. 8.2).

## 5. Модель данных

### 5.1. Общие правила для всех синхронизируемых таблиц

- Первичный ключ — **UUID**, генерируется на телефоне. Никаких автоинкрементов: иначе записи с разных телефонов конфликтуют.
- Служебные поля у каждой записи: `updated_at` (время изменения), `deleted` (мягкое удаление), `device_id` (с какого телефона изменено).
- Физически записи не удаляются, только помечаются.

### 5.2. Сущности

**Profile:** id, name, sd1_enabled, show_xe, carbs_per_xe.

**Product:** id, name, brand, barcode, kcal, protein, fat, carbs, fiber, sugar, salt, gi, piece_weight_g, source, notes, micro (JSON: код нутриента → значение на 100 г).

- Справочник нутриентов для `micro` зашит в приложение: код, название, единица (мг, мкг), суточная норма. В версии 1 это витамины A, C, D, E, K, B1, B2, B6, B9, B12 и минералы кальций, железо, магний, калий, натрий, цинк, фосфор, йод. Список расширяется без изменения схемы базы.

**Pan:** id, name, weight_g, photo (путь к файлу).

**Dish:** id, name, current_version_id.

**DishVersion** — неизменяемая после сохранения: id, dish_id, created_at, pan_id, gross_weight_g, net_weight_g (вычисленный вес нетто на момент сохранения).

**DishIngredient:** id, dish_version_id, product_id, weight_g.

**Meal:** id, profile_id, eaten_at, notes, glucose (null), insulin_dose (null).

**MealItem:** id, meal_id, type (product / dish), product_id или dish_version_id, weight_g, pieces (null), snapshot_kcal, snapshot_protein, snapshot_fat, snapshot_carbs.

### 5.3. Как считаются цифры

- КБЖУ и нутриенты продукта в порции: значение на 100 г × вес / 100.
- КБЖУ и нутриенты блюда на 100 г: сумма по ингредиентам версии / вес нетто × 100. Вес нетто = вес с кастрюлей − вес кастрюли; если вес не указан, берётся сумма сырых ингредиентов.
- Если продукт в базе дополнили (например, вписали витамины), статистика по прошлым приёмам пересчитывается с новыми данными.
- Поля `snapshot_*` в MealItem хранят КБЖУ на момент записи. Это защита на случай, если продукт позже испортили или удалили.

### 5.4. Версии блюд

- Приём пищи ссылается на **конкретную версию** блюда, а не на блюдо вообще. Сегодняшний суп и суп через неделю — разные версии с разным составом.
- Сохранённая и использованная в приёме пищи версия не редактируется. «Исправить опечатку в весе» у версии, которая ещё нигде не использована, можно.
- В списке и поиске видна только актуальная версия. Выбрать старую версию при записи можно через карточку блюда: «варки» — список версий с датами.
- «Сварил заново» копирует состав и кастрюлю, вес с кастрюлей остаётся пустым (новое взвешивание). Удалённая кастрюля не копируется.

### 5.5. Удаление продуктов, блюд и кастрюль

Удаление мягкое (5.1), с подтверждением.

- Удалённая запись пропадает из списков, поиска и выбора: в новые приёмы пищи и блюда её добавить нельзя.
- Записи, сделанные до удаления, не меняются: прошлые приёмы и варки показывают удалённый продукт или блюдо с прежним составом и КБЖУ.
- «Повторить» в истории пропускает удалённые продукты и блюда и сообщает об этом («Суп удалён и не добавлен»), остальной состав загружается.
- Удалённая кастрюля пропадает из выбора. Сохранённые варки не пересчитываются: вес нетто записан в версии; в списке варок кастрюля видна с пометкой «(удалена)».

## 6. Синхронизация

- **Когда:** при запуске приложения, после каждой записи или изменения (с задержкой в несколько секунд, чтобы собрать пачку изменений), периодически в фоне (WorkManager, примерно раз в 15 минут при наличии сети), по кнопке в настройках.
- **Протокол:**
  - телефон отправляет всё, что изменилось с момента последней успешной отправки;
  - затем забирает всё, что изменилось на сервере после его курсора синхронизации. Курсор — монотонный номер изменения на сервере, а не время: часы телефонов могут расходиться;
  - всё в одном запросе `POST /sync` или в двух, как удобнее при реализации.
- **Конфликты:** если одну запись изменили на двух телефонах, побеждает изменение, пришедшее на сервер позже. Для трёх пользователей этого достаточно. Версии блюд неизменяемы, поэтому по составу блюд конфликтов не бывает.
- **Фото кастрюль:** загружаются отдельным запросом, ссылка на файл синхронизируется вместе с записью.
- Ошибки синхронизации не блокируют работу. В настройках показывается статус и текст последней ошибки.


### 6.1. Первый запуск и новый телефон

1. Экран первого запуска: адрес сервера и ключ семьи, проверка соединения.
2. Загружается список профилей, пользователь выбирает владельца телефона. Если сервер пустой, профили создаются здесь же.
3. Полная загрузка всех данных с сервера: профили, продукты, кастрюли (фото догружаются в фоне), блюда со всеми версиями, приёмы пищи всех профилей. На экране виден прогресс.
4. Подключение к серверу можно пропустить и работать офлайн, а подключить позже в настройках.
5. Если на телефоне уже есть данные, а сервер не пустой: пользователь выбирает «отправить мои данные на сервер» (объединить) или «заменить данными сервера». Первый телефон, подключившийся к пустому серверу, просто отправляет всё.

Тот же сценарий работает при переустановке приложения: после удаления и новой установки все данные восстанавливаются с сервера. Теряется только то, что не успело синхронизироваться.

До этапа 1б (пока сервера нет) пункты 1 и 3 отсутствуют: профили создаются локально.

## 7. Дневник СД1 (только профили с флагом)

Показывается **только** для профиля с включённым флагом «Дневник СД1». У остальных профилей этих элементов нет нигде: ни при записи, ни в истории, ни в итогах.

- Углеводы приёма в граммах показываются крупно: именно их вводят в помпу. ХЕ показываются рядом, только если в профиле включён показ ХЕ.
- Необязательные поля приёма: **сахар** (ммоль/л) и **доза** (ед.). Это простые числа для истории, **без каких-либо расчётов доз**.
- В истории у таких приёмов видны сахар, доза и углеводы (и ХЕ, если включены).

Расчёт дозы, растянутый болюс, коэффициенты и прочий функционал СД1 в версию 1 не входят. Решение по ним принимается по итогам эксплуатации.

## 8. Обновление приложения

Механизм из GlucoPlan сохраняется, с доработками. Отдельных веток для разработки нет: каждый push в `main` даёт релиз, но на телефоны он ставится только вручную, по кнопке. Сначала новую версию ставит и проверяет Иван, потом говорит остальным обновиться.

### 8.1. Сборка (GitHub Actions)

При каждом push в `main`:

1. Автоматически увеличивается `VERSION_PATCH` в `version.properties`, коммит с `[skip ci]`.
2. **Запускаются unit-тесты** (`./gradlew testReleaseUnitTest`). Если тесты упали, релиза нет. *В текущем GlucoPlan этого шага нет: workflow сразу собирает APK.*
3. Сборка подписанного APK (ключ из секретов репозитория: `KEYSTORE_BASE64`, `KEYSTORE_PASSWORD`, `KEY_ALIAS`, `KEY_PASSWORD`), проверка подписи.
4. Создание GitHub Release с тегом `vX.Y.Z`, описанием из сообщения коммита и APK во вложении. Все релизы сохраняются, старые не удаляются.

### 8.2. В приложении

- Проверка наличия обновления через `GET https://api.github.com/repos/<owner>/<repo>/releases/latest`, сравнение версии из тега с текущей.
- **Когда проверять:** при запуске приложения (не чаще раза в час) и при открытии экрана настроек.
- **Никаких всплывающих окон.** Если обновление есть, на вкладке «Настройки» появляется точка-индикатор.
- В настройках блок «Обновление»:
  - текущая версия и доступная версия, описание изменений из релиза;
  - кнопка **«Обновить»**: активна, только если есть новая версия, иначе серая и недоступна;
  - кнопка «Проверить сейчас».
- По нажатию «Обновить»:
  1. синхронизация с сервером (с этапа 1б). Если не удалась — предупреждение «на телефоне есть неотправленные данные, всё равно обновить?»;
  2. скачивание APK с прогрессом;
  3. запуск системной установки. Нужны разрешение `REQUEST_INSTALL_PACKAGES` и FileProvider.

### 8.3. Откат на предыдущую версию

Android **не устанавливает более старую версию поверх новой**: установка APK с меньшим номером версии завершится ошибкой. Поэтому откат делается одним из двух способов:

- **Основной:** отменить изменения в git (`git revert`) и запушить. CI соберёт новую версию с номером выше, но со старым кодом, и она ставится обычным обновлением.
- **Аварийный:** удалить приложение, установить нужный APK из релизов, ввести адрес сервера и ключ. Данные восстановятся с сервера (раздел 6.1).

### 8.4. Сохранность данных

- Схема базы меняется только через миграции Room, каждая миграция покрывается тестом.
- Если приложение видит базу более новой версии схемы, чем знает само (случай отката через `git revert`), оно не падает, а очищает локальную базу и полностью загружает данные с сервера, предупредив об этом пользователя.

### 8.5. Требования

- Репозиторий должен быть **публичным**: API релизов для приватного репозитория требует токен, и проверка сломается.
- В APK и в репозиторий не попадают адрес сервера и ключ семьи. Они вводятся в настройках на телефоне.
- Ключ подписи хранится в надёжном месте вне GitHub: без него новые версии не установятся поверх старых.

## 9. Сервер

- FastAPI + SQLite, запуск через systemd, автозапуск после перезагрузки.
- **HTTPS обязателен.** Сертификат Let's Encrypt через Caddy как обратный прокси. Доменное имя — поддомен третьего уровня от хостера (при проблемах с выпуском сертификата — бесплатный DuckDNS).
- **Авторизация:** один ключ семьи в заголовке каждого запроса. Без ключа сервер отвечает 401.
- **Эндпоинты версии 1:** `GET /health`, `POST /sync`, `POST /photos`, `GET /photos/{id}`.
- **Резервная копия:** раз в сутки копия базы и папки фото, хранить последние 30 копий.
- В сервере с 1 ГБ ОЗУ и 2 ГБ swap нагрузка трёх телефонов укладывается с запасом.

## 10. Качество

- Unit-тесты обязательны для: расчёта КБЖУ продукта и блюда (с кастрюлей и без), итогов приёма, пересчёта штук в граммы, версий блюд (старые приёмы не меняются), логики синхронизации (порядок, конфликты, мягкое удаление), сравнения версий при обновлении, миграций базы.
- Интерфейс только на русском, светлая и тёмная тема.
- Минимальная версия Android — 10 (API 29), как в GlucoPlan.

---

## 11. Процесс разработки

- Код пишет Claude Code на сервере, в папке проекта. Задания даёт Иван по этапам ТЗ, небольшими подзадачами.
- Android-приложение на сервере не собирается: у сервера мало памяти. Сборку и тесты выполняет GitHub Actions.
- Push в `main` делается только после завершённой подзадачи. Каждый push — это релиз.
- Перед push: `git pull --rebase` (CI сам коммитит номер версии).
- После push Claude дожидается результата сборки (`gh run watch`). Если сборка или тесты упали, читает лог (`gh run view --log-failed`), исправляет и пушит снова, пока сборка не пройдёт.
- Серверная часть (этап 1б) тестируется прямо на сервере (pytest).
- Требования меняются только с согласия Ивана. Если код расходится с ТЗ или ТЗ неполно, Claude спрашивает, а не додумывает.

## 14. Принятые решения

1. Название: **«Еда и здоровье»**.
2. Новый `applicationId`: приложение ставится рядом с GlucoPlan, старое удаляется, когда новое освоено.
3. Новый публичный репозиторий. Ключ подписи — старый от GlucoPlan, если он сохранился, иначе новый.
4. Домен: поддомен третьего уровня от хостера.
5. Сканер штрихкода камерой входит в этап 1а.
6. ГИ у продуктов есть с первой версии.
7. ХЕ выключены по умолчанию, включаются и настраиваются в профиле.
8. Отдельной ветки для разработки нет. Установка обновлений только вручную, по кнопке в настройках.
