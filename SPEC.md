# ТЗ: «Еда и здоровье», версия 1

Черновик от 25.09.2026. Документ живёт в репозитории проекта, все изменения требований вносятся сюда.

---

## 1. Цель

Android-приложение «Еда и здоровье» для семьи из трёх человек: удобно взвешивать и записывать еду, считать КБЖУ, вести общую базу продуктов, блюд и кастрюль и синхронизировать всё через свой сервер. Собранные данные потом используются для отчётов и анализа (это следующие этапы, не версия 1).

Новый проект, пишется с нуля. Из старого GlucoPlan переносятся только отдельные куски кода: логика блюд и кастрюль, механизм обновления, CI. Старые данные не переносятся.

### Принципы

1. **Ввод должен быть быстрым.** Главный критерий качества — сколько нажатий и секунд уходит на запись приёма пищи.
2. **Телефон работает без интернета.** Все функции доступны офлайн, синхронизация догоняет, когда появляется сеть.
3. **История не меняется задним числом.** Правка продукта или блюда не должна тихо менять состав прошлых приёмов пищи (см. 5.4).
4. **Лучше меньше, но удобно.** Функции добавляются этапами, только когда в них появилась реальная потребность.

## 2. Пользователи и профили

- Три профиля: Иван, жена, дочь. Профили — общая сущность, синхронизируются между телефонами. Новый профиль можно добавить с любого телефона.
- Паролей и прав доступа нет, все могут всё.
- У каждого телефона есть **владелец**: профиль, выбранный в настройках при первом запуске из списка профилей. Выбор хранится только на этом телефоне.
- При записи приёма пищи вверху экрана выбирается, **кому** он записывается. По умолчанию это владелец телефона, переключается одним нажатием.
- У профиля есть флаг **«Дневник СД1»** (см. раздел 7). Включён только у дочери.
- Поля профиля: имя, флаг «Дневник СД1», показывать ли ХЕ (по умолчанию выключено), граммов углеводов в 1 ХЕ (только при включённом показе ХЕ).

## 3. Архитектура

```
 Телефон 1 ─┐
 Телефон 2 ─┼──HTTPS──  Сервер (Германия, Linux)
 Телефон 3 ─┘            API на Python + SQLite
```

- **Телефон:** Kotlin, Jetpack Compose, Room, Hilt (тот же стек, что в GlucoPlan). Локальная база — полноценная копия данных семьи.
- **Сервер:** Python (FastAPI), база SQLite, HTTPS, работает как systemd-сервис. Сервер — точка обмена и резервная копия, но телефон от него не зависит.
- **Общие данные** (видны и редактируются всеми): профили, продукты, кастрюли, блюда.
- **Личные данные:** приёмы пищи. Каждый хранится с идентификатором профиля. Видеть историю других профилей на телефоне можно (например, мама смотрит, что дочь ела с папой).

## 4. Экраны версии 1

Нижняя навигация: **Приём пищи · История · Продукты · Блюда · Настройки**. Кастрюли открываются из экрана «Блюда» или из настроек.

### 4.1. Приём пищи (главный экран)

- Вверху: выбор профиля («кому») и время приёма. По умолчанию время текущее, его можно изменить на прошедшее.
- Список позиций приёма. У каждой видны название, вес и КБЖУ порции; вес редактируется прямо в строке.
- Добавление позиции:
  - один общий поиск по продуктам и блюдам;
  - в начале списка без ввода текста стоят недавние и частые позиции этого профиля;
  - после выбора сразу открывается цифровая клавиатура для веса;
  - для продукта со средним весом штуки можно ввести количество штук вместо граммов;
  - кнопка сканера штрихкода рядом с поиском: найденный продукт сразу добавляется, ненайденный открывает создание продукта с уже заполненным штрихкодом.
- Внизу итоги приёма: ккал, Б, Ж, У.
- Кнопка «Записать» сохраняет приём и очищает экран. Незаписанный приём не теряется при переключении вкладок и перезапуске приложения.
- Если у выбранного профиля включён «Дневник СД1», дополнительно показываются поля из раздела 7.

### 4.2. История

- Список приёмов по дням, фильтр по профилю (по умолчанию владелец телефона) и по дате.
- У дня видны итоги КБЖУ, у приёма — время, состав и итоги.
- Приём можно открыть, отредактировать (вес позиций, время, состав) и удалить.
- «Повторить»: загрузить состав приёма на экран «Приём пищи» как новый приём.

### 4.3. Продукты

- Список с поиском (по названию и штрихкоду, в том числе сканером) и сортировкой (по названию, калориям, белкам, углеводам, ГИ). В строке — название и КБЖУ на 100 г.
- Карточка продукта:
  - **основное:** название, производитель (необязательно), штрихкод (необязательно, уникален, если указан; вводится вручную или сканером);
  - **на 100 г:** ккал, белки, жиры, углеводы, ГИ; необязательно: клетчатка, сахара, соль;
  - **средний вес штуки** в граммах, необязательно;
  - **источник данных:** этикетка / справочник / оценка / вручную;
  - **витамины и минералы:** раскрывающийся блок, все поля необязательные (см. 5.2);
  - заметка.
- Продукт можно удалить. Удаление мягкое: продукт пропадает из списков и поиска, но прошлые приёмы и блюда, где он использован, продолжают считаться.

### 4.4. Блюда

- Список блюд с поиском, в строке — КБЖУ на 100 г и дата последней варки.
- Редактор блюда:
  - название;
  - состав: продукты из базы с весом каждого, продукт в состав добавляется так же быстро, как в приём пищи;
  - выбор кастрюли из списка (с миниатюрой фото) и вес готового блюда вместе с кастрюлей;
  - приложение вычитает вес кастрюли и показывает вес нетто и КБЖУ на 100 г;
  - если вес не указан, расчёт идёт по сумме сырых ингредиентов, с явной пометкой об этом.
- «Сварил заново»: создаёт новую версию блюда на основе текущей. Состав и вес правятся под новую варку, старые приёмы пищи остаются со старой версией (см. 5.4).

### 4.5. Кастрюли

- Название, вес, фото (камера или галерея). Фото синхронизируется между телефонами.

### 4.6. Настройки

- Владелец этого телефона (выбор из профилей).
- Профили: список, добавление, редактирование, флаг «Дневник СД1», показ ХЕ и граммов в ХЕ.
- Сервер: адрес и ключ семьи, кнопка «Проверить соединение».
- Синхронизация: время последней успешной, кнопка «Синхронизировать сейчас», признак ошибки.
- Обновление: текущая и доступная версия, кнопки «Обновить» и «Проверить сейчас» (см. 8.2).

## 5. Модель данных

### 5.1. Общие правила для всех синхронизируемых таблиц

- Первичный ключ — **UUID**, генерируется на телефоне. Никаких автоинкрементов: иначе записи с разных телефонов конфликтуют.
- Служебные поля у каждой записи: `updated_at` (время изменения), `deleted` (мягкое удаление), `device_id` (с какого телефона изменено).
- Физически записи не удаляются, только помечаются.

### 5.2. Сущности

**Profile:** id, name, sd1_enabled, show_xe, carbs_per_xe.

**Product:** id, name, brand, barcode, kcal, protein, fat, carbs, fiber, sugar, salt, gi, piece_weight_g, source, notes, micro (JSON: код нутриента → значение на 100 г).

- Справочник нутриентов для `micro` зашит в приложение: код, название, единица (мг, мкг), суточная норма. В версии 1 это витамины A, C, D, E, K, B1, B2, B6, B9, B12 и минералы кальций, железо, магний, калий, натрий, цинк, фосфор, йод. Список расширяется без изменения схемы базы.

**Pan:** id, name, weight_g, photo (путь к файлу).

**Dish:** id, name, current_version_id.

**DishVersion** — неизменяемая после сохранения: id, dish_id, created_at, pan_id, gross_weight_g, net_weight_g (вычисленный вес нетто на момент сохранения).

**DishIngredient:** id, dish_version_id, product_id, weight_g.

**Meal:** id, profile_id, eaten_at, notes, glucose (null), insulin_dose (null).

**MealItem:** id, meal_id, type (product / dish), product_id или dish_version_id, weight_g, pieces (null), snapshot_kcal, snapshot_protein, snapshot_fat, snapshot_carbs.

### 5.3. Как считаются цифры

- КБЖУ и нутриенты продукта в порции: значение на 100 г × вес / 100.
- КБЖУ и нутриенты блюда на 100 г: сумма по ингредиентам версии / вес нетто × 100. Вес нетто = вес с кастрюлей − вес кастрюли; если вес не указан, берётся сумма сырых ингредиентов.
- Если продукт в базе дополнили (например, вписали витамины), статистика по прошлым приёмам пересчитывается с новыми данными.
- Поля `snapshot_*` в MealItem хранят КБЖУ на момент записи. Это защита на случай, если продукт позже испортили или удалили.

### 5.4. Версии блюд

- Приём пищи ссылается на **конкретную версию** блюда, а не на блюдо вообще. Сегодняшний суп и суп через неделю — разные версии с разным составом.
- Сохранённая и использованная в приёме пищи версия не редактируется. «Исправить опечатку в весе» у версии, которая ещё нигде не использована, можно.
- В списке и поиске видна только актуальная версия. Выбрать старую версию при записи можно через карточку блюда: «варки» — список версий с датами.
- «Сварил заново» копирует состав и кастрюлю, вес с кастрюлей остаётся пустым (новое взвешивание). Удалённая кастрюля не копируется.

### 5.5. Удаление продуктов, блюд и кастрюль

Удаление мягкое (5.1), с подтверждением.

- Удалённая запись пропадает из списков, поиска и выбора: в новые приёмы пищи и блюда её добавить нельзя.
- Записи, сделанные до удаления, не меняются: прошлые приёмы и варки показывают удалённый продукт или блюдо с прежним составом и КБЖУ.
- «Повторить» в истории пропускает удалённые продукты и блюда и сообщает об этом («Суп удалён и не добавлен»), остальной состав загружается.
- Удалённая кастрюля пропадает из выбора. Сохранённые варки не пересчитываются: вес нетто записан в версии; в списке варок кастрюля видна с пометкой «(удалена)».

## 6. Синхронизация

- **Когда:** при запуске приложения, после каждой записи или изменения (с задержкой в несколько секунд, чтобы собрать пачку изменений), периодически в фоне (WorkManager, примерно раз в 15 минут при наличии сети), по кнопке в настройках.
- **Протокол:**
  - телефон отправляет всё, что изменилось с момента последней успешной отправки;
  - затем забирает всё, что изменилось на сервере после его курсора синхронизации. Курсор — монотонный номер изменения на сервере, а не время: часы телефонов могут расходиться;
  - всё в одном запросе `POST /sync` или в двух, как удобнее при реализации.
- **Конфликты:** если одну запись изменили на двух телефонах, побеждает изменение, пришедшее на сервер позже. Для трёх пользователей этого достаточно. Версии блюд неизменяемы, поэтому по составу блюд конфликтов не бывает.
- **Фото кастрюль:** загружаются отдельным запросом, ссылка на файл синхронизируется вместе с записью.
- Ошибки синхронизации не блокируют работу. В настройках показывается статус и текст последней ошибки.

### 6.1. Первый запуск и новый телефон

1. Экран первого запуска: адрес сервера и ключ семьи, проверка соединения.
2. Загружается список профилей, пользователь выбирает владельца телефона. Если сервер пустой, профили создаются здесь же.
3. Полная загрузка всех данных с сервера: профили, продукты, кастрюли (фото догружаются в фоне), блюда со всеми версиями, приёмы пищи всех профилей. На экране виден прогресс.
4. Подключение к серверу можно пропустить и работать офлайн, а подключить позже в настройках.
5. Если на телефоне уже есть данные, а сервер не пустой: пользователь выбирает «отправить мои данные на сервер» (объединить) или «заменить данными сервера». Первый телефон, подключившийся к пустому серверу, просто отправляет всё.

Тот же сценарий работает при переустановке приложения: после удаления и новой установки все данные восстанавливаются с сервера. Теряется только то, что не успело синхронизироваться.

До этапа 1б (пока сервера нет) пункты 1 и 3 отсутствуют: профили создаются локально.

## 7. Дневник СД1 (только профили с флагом)

Показывается **только** для профиля с включённым флагом «Дневник СД1». У остальных профилей этих элементов нет нигде: ни при записи, ни в истории, ни в итогах.

- Углеводы приёма в граммах показываются крупно: именно их вводят в помпу. ХЕ показываются рядом, только если в профиле включён показ ХЕ.
- Необязательные поля приёма: **сахар** (ммоль/л) и **доза** (ед.). Это простые числа для истории, **без каких-либо расчётов доз**.
- В истории у таких приёмов видны сахар, доза и углеводы (и ХЕ, если включены).

Расчёт дозы, растянутый болюс, коэффициенты и прочий функционал СД1 в версию 1 не входят. Решение по ним принимается по итогам эксплуатации.

## 8. Обновление приложения

Механизм из GlucoPlan сохраняется, с доработками. Отдельных веток для разработки нет: каждый push в `main` даёт релиз, но на телефоны он ставится только вручную, по кнопке. Сначала новую версию ставит и проверяет Иван, потом говорит остальным обновиться.

### 8.1. Сборка (GitHub Actions)

При каждом push в `main`:

1. Автоматически увеличивается `VERSION_PATCH` в `version.properties`, коммит с `[skip ci]`.
2. **Запускаются unit-тесты** (`./gradlew testReleaseUnitTest`). Если тесты упали, релиза нет. *В текущем GlucoPlan этого шага нет: workflow сразу собирает APK.*
3. Сборка подписанного APK (ключ из секретов репозитория: `KEYSTORE_BASE64`, `KEYSTORE_PASSWORD`, `KEY_ALIAS`, `KEY_PASSWORD`), проверка подписи.
4. Создание GitHub Release с тегом `vX.Y.Z`, описанием из сообщения коммита и APK во вложении. Все релизы сохраняются, старые не удаляются.

### 8.2. В приложении

- Проверка наличия обновления через `GET https://api.github.com/repos/<owner>/<repo>/releases/latest`, сравнение версии из тега с текущей.
- **Когда проверять:** при запуске приложения (не чаще раза в час) и при открытии экрана настроек.
- **Никаких всплывающих окон.** Если обновление есть, на вкладке «Настройки» появляется точка-индикатор.
- В настройках блок «Обновление»:
  - текущая версия и доступная версия, описание изменений из релиза;
  - кнопка **«Обновить»**: активна, только если есть новая версия, иначе серая и недоступна;
  - кнопка «Проверить сейчас».
- По нажатию «Обновить»:
  1. синхронизация с сервером (с этапа 1б). Если не удалась — предупреждение «на телефоне есть неотправленные данные, всё равно обновить?»;
  2. скачивание APK с прогрессом;
  3. запуск системной установки. Нужны разрешение `REQUEST_INSTALL_PACKAGES` и FileProvider.

### 8.3. Откат на предыдущую версию

Android **не устанавливает более старую версию поверх новой**: установка APK с меньшим номером версии завершится ошибкой. Поэтому откат делается одним из двух способов:

- **Основной:** отменить изменения в git (`git revert`) и запушить. CI соберёт новую версию с номером выше, но со старым кодом, и она ставится обычным обновлением.
- **Аварийный:** удалить приложение, установить нужный APK из релизов, ввести адрес сервера и ключ. Данные восстановятся с сервера (раздел 6.1).

### 8.4. Сохранность данных

- Схема базы меняется только через миграции Room, каждая миграция покрывается тестом.
- Если приложение видит базу более новой версии схемы, чем знает само (случай отката через `git revert`), оно не падает, а очищает локальную базу и полностью загружает данные с сервера, предупредив об этом пользователя.

### 8.5. Требования

- Репозиторий должен быть **публичным**: API релизов для приватного репозитория требует токен, и проверка сломается.
- В APK и в репозиторий не попадают адрес сервера и ключ семьи. Они вводятся в настройках на телефоне.
- Ключ подписи хранится в надёжном месте вне GitHub: без него новые версии не установятся поверх старых.

## 9. Сервер

- FastAPI + SQLite, запуск через systemd, автозапуск после перезагрузки.
- **HTTPS обязателен.** Сертификат Let's Encrypt через Caddy как обратный прокси. Доменное имя — поддомен третьего уровня от хостера (при проблемах с выпуском сертификата — бесплатный DuckDNS).
- **Авторизация:** один ключ семьи в заголовке каждого запроса. Без ключа сервер отвечает 401.
- **Эндпоинты версии 1:** `GET /health`, `POST /sync`, `POST /photos`, `GET /photos/{id}`.
- **Резервная копия:** раз в сутки копия базы и папки фото, хранить последние 30 копий.
- В сервере с 1 ГБ ОЗУ и 2 ГБ swap нагрузка трёх телефонов укладывается с запасом.

## 10. Качество

## 11. Процесс разработки

- Код пишет Claude Code на сервере, в папке проекта. Задания даёт Иван по этапам ТЗ, небольшими подзадачами.
- Android-приложение на сервере не собирается: у сервера мало памяти. Сборку и тесты выполняет GitHub Actions.
- Push в `main` делается только после завершённой подзадачи. Каждый push — это релиз.
- Перед push: `git pull --rebase` (CI сам коммитит номер версии).
- После push Claude дожидается результата сборки (`gh run watch`). Если сборка или тесты упали, читает лог (`gh run view --log-failed`), исправляет и пушит снова, пока сборка не пройдёт.
- Серверная часть (этап 1б) тестируется прямо на сервере (pytest).
- Требования меняются только с согласия Ивана. Если код расходится с ТЗ или ТЗ неполно, Claude спрашивает, а не додумывает.

## 15. Этап 2: замеры

Черновик от 29.09.2026, по ответам в `docs/voprosy-etap-2.md`.

### 15.1. Цель

Записывать замеры тела рядом с едой, чтобы следить за весом, контролировать похудение и искать связь еды с самочувствием. Анализ, графики и цели — этап 3; в этапе 2 данные только вводятся и видны в истории.

Принципы раздела 1 действуют: быстрый ввод, работа без интернета, синхронизация как у остальных данных (раздел 6).

### 15.2. Что записываем

| Замер | Поля | Кто пользуется | Как часто |
|---|---|---|---|
| **Вес** | кг, точность 0,1 | все | Иван — каждый день, иногда утром и вечером; дочь — раз в месяц; жена — редко |
| **Давление и пульс** | верхнее, нижнее, пульс — одно измерение, без серий и дополнительных полей | Иван, жена | жена — несколько раз в день, Иван — раз в день |
| **Сон** | время засыпания и пробуждения; длительность считается; оценка «плохо / нормально / хорошо» — необязательно | все | каждую ночь |
| **Вода** | мл, только чистая вода (чай, суп и другие напитки — это еда) | Иван | несколько раз в день |
| **Обхваты тела** | см: шея, грудь, талия, живот (по пупку), бёдра (таз), бедро, голень, плечо, запястье; одна (правая) сторона; любое поле можно пропустить | Иван | примерно раз в неделю |
| **Рост** | см | все; у дочери меняется | при изменении |

- У каждой записи — **дата и время** замера (по умолчанию «сейчас», можно указать прошедшее, как у приёма пищи). Никаких других пометок («натощак» и т. п.) не нужно.
- Замеры можно вводить **любому** члену семьи (выбор «кому», как у приёма пищи, по умолчанию владелец телефона). Видят все.
- Подсветки «плохих» значений, целей и норм, кроме нормы воды, в этапе 2 нет.
- **Уведомлений и напоминаний нет** совсем.

Проверка ввода (от опечаток, не медицинские границы): вес 2–300 кг; давление: верхнее 50–260, нижнее 30–160, пульс 30–220; сон: пробуждение позже засыпания, не дольше 20 часов; вода 1–3000 мл за раз; обхваты 5–250 см; рост 30–250 см.

### 15.3. Профиль

В профиль добавляются:
- **пол** и **дата рождения** — для роста дочери по возрасту и норм витаминов и минералов в отчётах этапа 3 (сейчас в справочнике 5.2 нормы для взрослого мужчины);
- **рост** — задаётся в настройках профиля. Каждое изменение сохраняется с датой, история роста синхронизируется: у дочери по ней видно, как она растёт;
- **вода**: флаг «Считать воду» (по умолчанию выключен, включён только у Ивана) и **норма, мл на 1 кг веса** (по умолчанию 30). Дневная норма = норма × последний записанный вес.

### 15.4. Интерфейс

- На экране «Приём пищи» — кнопка **«+ Замер»**. Она открывает отдельный экран со списком замеров: **вес и давление первыми** (вводятся чаще всего), дальше сон, вода, обхваты. Основной экран больше ничем не загромождается.
- Ввод одного замера — экран или диалог с цифровой клавиатурой, «кому» и временем, кнопка «Записать». Для веса подсказкой видно последнее значение этого человека.
- **Вода**: в поле подставлен последний введённый объём, «Записать» — одним нажатием. На экране видно «выпито за сегодня 1,2 из 2,3 л» и сегодняшние записи; любую можно исправить или удалить. Вода показывается только у профилей с флагом «Считать воду».
- **История**: замеры показываются **в той же ленте, что и еда, по времени**. Нажатие — исправить или удалить (удаление мягкое, 5.1). Воду, чтобы не засорять ленту, предлагается показывать одной строкой за день («Вода 1,8 из 2,3 л»), а не каждый стакан.
- Отдельных списков и графиков замеров в этапе 2 нет — они в отчётах этапа 3.

### 15.5. Health Connect (пробно)

У Ивана и жены браслеты Mi Band с приложением Mi Fitness, которое пишет данные в Health Connect; весы и тонометр без Bluetooth.

- Последней подзадачей этапа пробуется **импорт сна из Health Connect** для владельца телефона: по кнопке или при открытии приложения, с пометкой источника, без повторов. Импортированную запись можно исправить, повторный импорт исправление не затирает.

## 17. Этап 3: отчёты, Telegram, анализ

Черновик от 30.09.2026, по ответам в `docs/voprosy-etap-3.md` и на вопросы к этому разделу.

### 17.1. Цель

Каждое утро каждый получает итоги вчерашнего дня, по понедельникам — итоги недели, 1-го числа — итоги месяца. Для Ивана главное — вес и нормы КБЖУ, для дочери — углеводы, сахар и состав еды, для всех — витамины и минералы. Раз в сутки Claude разбирает данные и даёт подробные советы. Отчёты приходят в Telegram и видны в приложении.

Порядок работ: ежедневный отчёт → недельный → месячный → копии базы в Telegram → анализ Claude → PDF для врача.

### 17.2. Где и как строятся отчёты

- **На сервере.** У него есть данные всех телефонов, и он работает в 6:00, когда телефоны спят. Один расчёт служит и Telegram, и приложению.
- Отчёт строится по тому, что дошло до сервера. Телефон отправляет изменения через несколько секунд после записи и проверяет каждые 15 минут, если есть сеть. Запись, сделанная без сети и не отправленная до 6:00, попадёт только в отчёт, сформированный позже вручную (17.10).
- Отчёты **не хранятся**: сервер строит их заново по запросу, это быстро. Хранится только последний анализ Claude на каждого (17.9).
- Графики — картинки PNG, одни и те же в Telegram и в приложении.
- Отчёты в приложении требуют интернета. Это исключение из принципа 2 (раздел 1): отчёты смотрят редко, запись еды и замеров по-прежнему работает офлайн.
- Часовой пояс — Москва, для всех. «Вчера» — с 00:00 до 24:00 по Москве.
- Нутриенты приёмов сервер считает по правилам 5.3, так же, как телефон. Для расчётов, которые есть и на телефоне, и на сервере (нутриенты, нормы), заводятся общие контрольные примеры, по ним проверяются обе стороны.

### 17.3. Нормы

**Новые поля профиля** (синхронизируются, меняются в настройках профиля без новой версии приложения):
- **активность**: сидячий / немного / умеренно / много, по умолчанию «умеренно»;
- **цель по весу**: целевой вес (необязательно) и темп, кг в неделю (по умолчанию 0,5). Без целевого веса — поддержание;
- **нормы вручную**: калории, белки, жиры, углеводы. Пустое поле — берётся расчёт; рядом всегда видно расчётное значение («расчёт: 2050 ккал»);
- **целевой диапазон сахара**, ммоль/л «от — до» — только у профиля с флагом «Дневник СД1».

**Расчёт:**
- Взрослые (18 лет и старше): базовый обмен по формуле Миффлина — Сан Жеора (пол, возраст, последний рост и вес) × коэффициент активности (1,2 / 1,375 / 1,55 / 1,725). При цели похудеть — минус темп × 7700 / 7 ккал в день (0,5 кг в неделю ≈ 550 ккал), но не меньше базового обмена. Цель достигнута — норма на поддержание.
- Дети (до 18 лет): калории, белки, жиры, углеводы — по МР 2.3.1.0253-21 для возраста и пола. Цели по весу у детей нет.
- БЖУ взрослых из калорий: белки 20 %, жиры 30 %, углеводы 50 %. Клетчатка — не меньше 25 г, соль — не больше 5 г.
- Витамины и минералы — по МР 2.3.1.0253-21 для пола и возраста, детям — детские нормы. Это заменяет единую «мужскую» норму справочника из 5.2.
- Норма пересчитывается по последнему весу на тот день, поэтому у прошлых дней она такая, какой была тогда.

- **Полнота данных о витаминах.** Витамины и минералы считаются только по продуктам, у которых они заполнены, а на упаковках их обычно нет. Поэтому отчёт показывает, для какой доли съеденного они известны («витамины известны для 35 % калорий»). Справочник химсостава (таблицы Скурихина или USDA: найти продукт и подставить витамины) подключается после этапа 3 (раздел 12, «После этапа 3»).

### 17.4. Активность (задел)

В отчётах есть место под активность: шаги, упражнения, потраченные калории. Пока там пусто, а расход оценивается по коэффициенту активности из профиля. Учёт активности — шаги из Health Connect и ручной ввод упражнений (приседания, отжимания, подтягивания и т. д.) — делается отдельно, после чего в нормы и отчёты пойдёт фактический расход.

Учёт активности — отдельный этап после этапа 3 (раздел 12).

### 17.5. Ежедневный отчёт

- В **6:00** за вчерашний день, каждому (кому что приходит — 17.7). В приложении — в любой момент, в том числе за сегодня, пока день не закончился (17.10).
- Сначала **краткая выжимка** (5–8 строк), под ней **подробности**. В Telegram подробности спрятаны в сворачиваемый блок: развернёт, кому интересно.

**Выжимка:**
- калории: 1850 из 2050 (90 %); белки, жиры, углеводы — факт и норма;
- вес утром и изменение к вчерашнему дню и к неделе назад; сколько осталось до цели;
- сон: длительность, во сколько лёг и встал, оценка;
- вода: 1,8 из 2,3 л — у тех, у кого она считается;
- давление и пульс, если записаны;
- 1–3 главных замечания по правилам: «белка 60 % нормы», «клетчатка 12 г из 25», «соль 8 г при норме 5».

**Подробности:**
- приёмы пищи по времени: состав и КБЖУ каждого;
- витамины и минералы: чего не хватило (меньше 70 % нормы), что в норме, что с перебором;
- все измерения давления; обхваты и рост, если записаны;
- активность — задел (17.4).

**Для профиля с СД1** дополнительно:
- в выжимке — углеводы за день крупно, число приёмов; сахар при приёмах, если записан, и сколько замеров в целевом диапазоне;
- в подробностях по каждому приёму: **время**, **углеводы жирным** (и ХЕ, если включены), состав, сахар и доза, если записаны. Так отчёт удобно положить рядом с графиком Libre: «в 12:00 сладкий сок — 25 г углеводов».

**Мало данных:** если за день записано меньше двух приёмов пищи или калорий меньше половины нормы, в выжимке пометка «возможно, данные неполные». Если за день не записано ничего, приходит одна строка: «За вчера ничего не записано».

**Данные сенсора Libre 2** в этап 3 не входят: время и углеводы приёмов сравниваются с графиком в LibreLink глазами. Сахар с сенсора подключается отдельно после этапа 3 (раздел 12, «После этапа 3»), вероятно через LibreLinkUp: сервер забирает сахар через аккаунт наблюдателя (неофициальный способ, может сломаться). Другие варианты — Nightscout, выгрузка CSV из LibreView. Пока данных сенсора нет, Claude оценивает компенсацию только по сахару, записанному при приёмах пищи.

### 17.6. Недельный и месячный отчёты

- **Недельный** — в понедельник в 6:00 за прошлую неделю (понедельник — воскресенье). **Месячный** — 1-го числа в 6:00 за прошлый месяц. Приходят после ежедневного отчёта.
- Так же: выжимка, подробности, картинки. У каждой цифры — сравнение с прошлой неделей или месяцем (↑ ↓ и разница).

**Содержание:**
- средние калории и БЖУ в день (по дням, где записана еда) и % нормы; дни с перебором (больше 110 % калорий) и недобором (меньше 80 %);
- вес: начало и конец периода, изменение, средний темп в неделю против целевого, прогноз даты достижения цели при таком темпе;
- сон: средняя длительность, среднее время отбоя и подъёма, разброс времени отбоя (режим), средняя оценка;
- давление и пульс: средние, минимум и максимум, число измерений;
- вода: в среднем за день, в скольких днях выпита норма;
- витамины и минералы: средний % нормы, постоянные нехватки;
- частые продукты и блюда: топ-10 по числу раз и главные источники калорий;
- обхваты: изменение за период (талия, живот и др.);
- полнота записей: «еда записана в 6 днях из 7»;
- для профиля с СД1: углеводы в день; средние углеводы на завтрак, обед, ужин и перекусы (по времени приёма); сахар при приёмах — средний и доля в целевом диапазоне; рост, если записан.

**Картинки** (только если есть данные): вес по дням с линией тренда и цели; калории по дням с линией нормы; сон по дням (длительность и время отбоя); давление и пульс; для профиля с СД1 — углеводы по дням и сахар при приёмах точками на фоне целевого диапазона.

### 17.7. Telegram

- Бота создаёт Иван через @BotFather. Токен хранится только на сервере, в репозиторий не попадает.
- Бот **только отправляет** сообщения и на команды не отвечает.
- **Привязка:** каждый пишет боту `/start`. Иван запускает на сервере скрипт `server/deploy/telegram-setup.sh`. Скрипт спрашивает токен (если его ещё нет), показывает, кто писал боту, и для каждого человека спрашивает, чьи отчёты ему присылать (выбор из профилей). Результат сохраняется в конфиг на сервере, его можно поправить и руками. В конце каждому уходит пробное сообщение.
- Кто что получает (1.4 в вопросах): Иван — свои отчёты и дочери, жена — свои и дочери, дочь — свои.
- Сообщения одному человеку идут по порядку: на каждый профиль — ежедневный отчёт, недельный, месячный, затем анализ Claude.
- Если Telegram недоступен, сервер повторяет отправку несколько раз в течение часа, ошибка пишется в журнал сервиса.
- Отчёты, в том числе дочери, хранятся в облаке Telegram — это данные о здоровье за пределами своего сервера.
- Не в этапе 3: общий семейный чат, настройка времени, отключение отчётов (убрать получателя можно правкой конфига).

### 17.8. Копии базы в Telegram

- Каждый день после резервной копии (3:30) Ивану в тот же чат приходит полная копия — база и фото кастрюль одним сжатым архивом, без звука. Ключ семьи и токен бота в архив не входят. Кому присылать, выбирается в `telegram-setup.sh`.
- Если файл больше лимита бота (50 МБ), он делится на части; в сообщении — как собрать и восстановить (`restore.sh`).

- Копия не шифруется: её откроет любой, у кого есть доступ к Telegram Ивана. Шифрование паролем можно добавить позже.

### 17.9. Анализ Claude

**Без ключа API.** На этом же сервере установлен Claude Code под учётной записью `ivan` (подписка). Ночью он запускается по таймеру:
1. В 4:00 сервер выгружает на каждого человека текстовый файл с данными: вчерашний день подробно, сводки за 7 и 30 дней, профиль, нормы, цели, целевой диапазон сахара.
2. Таймер от имени `ivan` запускает Claude Code в неинтерактивном режиме (`claude -p`) отдельно по каждому человеку. Промт берётся из файла, данные передаются на вход. Инструменты отключены: Claude только читает присланное и пишет ответ, ни файлов, ни команд не трогает. Ответ сохраняется в файл.
3. В 6:00 анализ уходит в Telegram вслед за отчётами и виден в приложении (17.10). Хранится только последний, прошлые не нужны.

- **Периоды:** один ночной запуск разбирает сразу вчерашний день, последнюю неделю и последний месяц — три раздела в одном ответе.
- **Что анализирует:** всё — сбалансированность питания, нехватки, ход похудения, связь еды со сном и давлением; для дочери — связь еды и сахара, качество компенсации диабета.
- **Тон:** подробно, с объяснениями и конкретными советами.
- **Для дочери — советы по компенсации, в том числе про инсулин** (ответ 6.7). Это не противоречит разделу 7: там запрет на расчёты доз в приложении, здесь — текстовые советы. В промте закладывается: советы по дозам и коэффициентам опираются на данные и подаются как предложения, которые стоит обсудить с эндокринологом. Диагнозов Claude не ставит.
- **Промты** — текстовые файлы на сервере: общий плюс свой на каждого (для дочери — про СД1). Образцы лежат в репозитории, рабочие копии — в папке данных сервера. Правятся без новой версии, установка и обновление их не перезаписывают.
- Данные при анализе уходят в Anthropic (так работает Claude Code), в том числе данные дочери.
- Три запуска в сутки расходуют лимиты подписки Ивана. Если запуск не удался (лимит, истёк вход, нет сети), отчёты уходят без анализа, а Ивану приходит короткое сообщение об ошибке.
- Памяти у сервера 1 ГБ. Запуски идут по очереди, ночью; если Claude Code в это время открыт интерактивно, памяти может не хватить. Это проверяется на первой подзадаче анализа.

- Кнопки «Проанализировать сейчас» нет: анализ только ночью, по кнопке в приложении строятся отчёты (они без Claude). Для проверки на сервере есть `analysis-now.sh`.
- **Как устроено** (подзадача 3-7): папка обмена `analysis/` в папке данных, пользователь `ivan` входит в группу сервиса. Свой промт профиля — файл с его именем; без него — `sd1.md` для профиля с «Дневником СД1», иначе `adult.md`. Анализ делается на каждый профиль семьи. Ответ Claude пишет с заголовками «##»: текст до первого заголовка — выжимка, разделы — подробности, как у отчётов. Сообщение о сбое получает тот, кто выбран для копий базы (17.8). Проверено: Claude Code занимает около 250 МБ, ответ — 20–60 секунд.

### 17.10. Приложение: экран «Отчёты и анализ»

- Открывается кнопкой в «Настройках», отдельным экраном. Нижняя навигация не меняется.
- Показываются отчёты и анализ **только владельца телефона**, переключения на других нет. Отчёты дочери родители получают в Telegram (17.7). Вкладки: **День · Неделя · Месяц · Анализ**. Период листается стрелками ← →; по умолчанию вчера, прошлая неделя, прошлый месяц.
- Показываются те же текст и картинки, что в Telegram.
- Кнопка **«Сформировать сейчас»**: телефон синхронизируется, затем сервер строит отчёт за выбранный период, в том числе за сегодня, пока день не закончился. В Telegram такой отчёт не отправляется.
- Без интернета — сообщение «Отчёты доступны только при связи с сервером».
- В редакторе профиля — новые поля из 17.3.

### 17.11. PDF для врача

- Только для профиля с СД1 (дочь). Кнопка «PDF для врача» на экране «Отчёты и анализ» есть на любом телефоне, где в семье есть профиль с СД1: родители готовят PDF к приёму со своего телефона, хотя остальные отчёты дочери в приложении видны только у неё. Период выбирается (по умолчанию прошлый месяц). Готовый файл отправляется через «Поделиться» Android (в Telegram, почту и т. д.).
- Содержание: по дням — таблица приёмов (время, кратко состав, углеводы и ХЕ, сахар, доза), углеводы за день; за период — средние углеводы по времени суток, сахар при приёмах (средний и доля в диапазоне), вес и рост, график углеводов по дням.

### 17.12. Сервер

- Новые части: построение отчётов, графики (matplotlib, шрифт с кириллицей), PDF, отправка в Telegram, выгрузка для Claude. Логика отчётов покрывается тестами pytest.
- Новые эндпоинты: отчёт за период (текст и ссылки на картинки), картинка, последний анализ, PDF за период. Авторизация — ключ семьи, как у остальных.
- Таймеры systemd: 3:30 — очистка, копия, отправка копии в Telegram; 4:00 — выгрузка и анализ Claude; 6:00 — рассылка отчётов.
- Установка по-прежнему одним скриптом (`install.sh`): он ставит новые зависимости и таймеры. Токен бота и привязка чатов — через `telegram-setup.sh`. Таймер анализа ставится для пользователя `ivan`: Claude Code установлен под ним.
- Новые поля профиля хранятся в JSON записи, серверной схемы не меняют. На телефоне — миграция с тестом (8.4).

### 17.13. Не входит в этап 3

- Общий семейный чат, команды бота, настройка времени и отключение отчётов.
- Хранение прошлых анализов.
- Учёт активности (17.4), данные сенсора Libre (17.5), справочник химсостава (17.3), шифрование копий (17.8) — после этапа 3.
